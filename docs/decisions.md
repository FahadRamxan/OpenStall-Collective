# Decisions

Design decisions and the reasons for them, newest section last. Add to this file when you make a choice that someone would otherwise have to rediscover.

## October 30: the web app and its tests (prompt 02)

**Next.js 16 with create-next-app's defaults, Cache Components included.** `apps/web` was created with create-next-app 16.4 (TypeScript, App Router, Tailwind CSS 4, ESLint, `src/`, `@/*`). Its defaults turn on Cache Components and Partial Prefetching. We kept them: they are the default for new apps and become always on in the next major version, and they make server-side data dynamic unless cached, so `next build` never needs a running API. The cost:

- Anything that reads request data or unknown URL params needs a `<Suspense>` boundary, or `next build` fails. This includes `usePathname()` in the header on dynamic routes such as `/stall/[id]`, so the header's navigation is already wrapped in one (checked with a temporary dynamic route: without the boundary the build fails with `CLIENT_HOOK_DYNAMIC`).
- Pages you navigate away from stay in the DOM, hidden. UI tests find elements by role, label or text, which skip hidden elements.

We did not add the `AGENTS.md` and `CLAUDE.md` files that create-next-app can generate: agent instruction files are the team's call. `apps/web/README.md` points to the docs bundled in `node_modules/next/dist/docs/` instead.

**Vitest 5 with jsdom and React Testing Library.** Vitest runs `src/**/*.test.ts(x)` and the build-config checks next to `package.json` (`*.test.ts`), so it never picks up the Playwright specs in `e2e/`. The `@/*` alias resolves through Vite's own `resolve.tsconfigPaths` option, so the `vite-tsconfig-paths` plugin from the Next.js guide is not needed. The tests need Node 22.22.2+, 24.15+ or 26+ (jsdom 30 skips Node 25), so `package.json` asks for `^24.15.0 || >=26.0.0` and the READMEs say Node 24.15 or newer.

**No CI: one local command is the gate.** GitHub Actions can't run on the repo owner's account, so `scripts/check_all.py` runs every check before a push: `pytest`, then `npm run lint`, `npm test`, `npm run build` and `npm run e2e` in `apps/web`. It stops at the first failure and prints which checks passed, failed or did not run. It finds the repo from its own path, runs pytest on the repo's `.venv` Python when there is one (`.venv/Scripts/python.exe` on Windows, `.venv/bin/python` elsewhere, else the Python running it), passes that Python to the UI tests as `E2E_PYTHON`, and calls npm by the full path `shutil.which` finds (`npm.cmd` on Windows), never through a shell. We left `.github/workflows/ci.yml` as prompt 01 made it; removing it is a separate change. Later prompts add their checks to this script.

**UI tests run against their own servers.** Playwright starts the API on 127.0.0.1:8100 and the web app on 127.0.0.1:3100 (overridable with `E2E_API_PORT` and `E2E_WEB_PORT`) and never reuses a server that is already running, so a dev server on 8000 or 3000 can neither collide with the tests nor leak into them. Prompt 02 asked for 8000 and 3000; with those, `npm run e2e` and `check_all.py` would fail whenever the dev servers are running, which is most of the time. The web app is a production build served by `next start`, which is steadier than the dev server and is what we deploy; `NEXT_PUBLIC_API_BASE_URL` is set for that build, because Next.js bakes it in. Tests run one at a time because they share one API and one database.

**The UI tests build into `.next-e2e/`, not `.next`.** Their build talks to the e2e API, so in `.next` it would replace your own build, and `npm start` would then serve a site whose footer says the API is offline. `playwright.config.ts` sets `NEXT_DIST_DIR=.next-e2e` for the web server, and `next.config.ts` uses it as `distDir`. `tsconfig.json` lists `.next-e2e/types/**/*.ts` and `.next-e2e/dev/types/**/*.ts` up front, because otherwise `next build` adds them itself and changes a tracked file on every first run. ESLint and git ignore the folder. `build-config.test.ts` checks all of this.

**The e2e database starts empty on every run.** The API gets `DATABASE_URL` pointing at a SQLite file in `apps/web/.e2e-data/` (git-ignored). A small script in the API server's start command empties that folder just before the API starts. It is not done in `playwright.config.ts`, because Playwright loads the config in several processes, in UI mode even while the servers are running.

**Which Python runs the e2e API.** `E2E_PYTHON` if set, otherwise the repo's `.venv` (`.venv/Scripts/python.exe` on Windows, `.venv/bin/python` elsewhere), otherwise `python` from PATH.

**Geist comes from the `geist` npm package, not Google Fonts.** `next/font/google` downloads fonts during `next build`, so every build, and with it `npm run e2e` and `check_all.py`, needed internet access. The `geist` package (Vercel's, SIL Open Font License) ships the font files and loads them with `next/font/local`. It is pinned to 1.8.1 in the lockfile; 1.9.0 was hours old when we added it.

**CORS allows exactly one origin.** The API accepts browser calls only from `WEB_BASE_URL` (default http://localhost:3000, trailing slash removed because browsers send the origin without one), with no cookies. The MCP endpoint keeps its own host and origin checks.

**The footer checks the API.** A small status line in the footer calls `/health` through `src/lib/api.ts`. It is the first real use of the fetch wrapper, and the UI test that expects "API online" proves the API address baked into the build and the API's CORS setting fit together. Every visitor sees it, judges included, so when the check fails it says "API offline. Try again in a minute." rather than a developer message with the API's address; the failed request is in the browser console. It gives up after 10 seconds, so a hung API or a slow cold start on the hosted demo cannot leave it on "Checking the API…". It uses a timer rather than `AbortSignal.timeout` or `AbortSignal.any`, which older browsers lack.

**A styled "Page not found" page.** `src/app/not-found.tsx` replaces Next.js's default 404, which brought its own white background, system font and full-height block into our layout. Until stall pages exist, stall links land there.

## October 31: settings, fake mode and the adapter registry (prompt 03)

**One settings object, named like the environment.** `openstall_api/settings.py` is a pydantic-settings `Settings` class with one field per variable in `.env.example`, and each field is named after its variable (`settings.PAYPAL_CLIENT_ID`), so one search finds a setting in the code, in `.env.example` and in the host's dashboard. `get_settings()` reads it once per process, and the object is frozen. Secrets (`PAYPAL_CLIENT_SECRET`, `TWILIO_AUTH_TOKEN`, the model keys, `GOOGLE_VISION_API_KEY`, `PASSPORT_SIGNING_KEY`) are `SecretStr`, so printing or dumping the settings shows `**********`. A test checks that `.env.example` and `Settings` list the same variables.

**How settings load.** Environment variables win over `.env`. The `.env` is the one at the repo root, found from the code's own path rather than the working directory, as `load_dotenv()` found it before. An empty value means unset, so a fresh copy of `.env.example` changes nothing. Unknown variables in `.env` are ignored, so the web app's can live in the same file. `OPENSTALL_MODE` accepts any case, and both base URLs lose a trailing slash. `python-dotenv` is no longer a direct dependency: pydantic-settings brings it.

**Three settings arrive now: `OPENSTALL_MODE`, `LLM_MODEL` and `GOOGLE_VISION_API_KEY`.** The image search adapter needs a key to report on, so `GOOGLE_VISION_API_KEY` comes now rather than in prompt 37. `DATABASE_URL` defaults to `sqlite:///./data/openstall.db`, the default prompt 04 asks for. `.env.example` now leaves it empty, with the docker-compose Postgres URL in a comment, so a copied `.env.example` works without Docker.

**Where the adapters live.**

| Adapter | Interface and fake | Real service and keys |
|---|---|---|
| LLM | `packages/agents/openstall_agents/adapters/llm.py`: `LLM`, `FakeLLM` | Claude: `ANTHROPIC_API_KEY` |
| Speech to text | `packages/agents/openstall_agents/adapters/speech.py`: `SpeechToText`, `FakeSpeechToText` | OpenAI transcription, until `docs/day-one-checks.md` names another provider: `OPENAI_API_KEY` |
| Embedder | `packages/agents/openstall_agents/adapters/embedder.py`: `Embedder`, `FakeEmbedder` | OpenAI embeddings: `OPENAI_API_KEY` |
| Image search | `packages/agents/openstall_agents/adapters/image_search.py`: `ImageSearch`, `FakeImageSearch` | Google Cloud Vision: `GOOGLE_VISION_API_KEY` |
| Messenger | `apps/api/openstall_api/messaging.py`: `Messenger`, `FakeMessenger` | Twilio WhatsApp sandbox: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` |
| Payment gateway | `packages/paypal/openstall_paypal/gateway.py`: `PaymentGateway`, `FakeGateway` | PayPal sandbox: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` |

The registry is `apps/api/openstall_api/adapters.py`. Each `AdapterSpec` lists the keys its real implementation needs, with `make_fake` and `make_real`; `make_real` stays `None` until the prompt that builds the real adapter sets it. The interfaces are `runtime_checkable` Protocols, so a test can check that a fake or a real adapter fits. Photos and voice notes reach the AI adapters as `Media`: bytes and a content type.

**Two modes, and four adapter states rather than three.** Fake mode always uses the fakes, even when keys are set. Sandbox mode uses the real adapters and never falls back to a fake, so the hosted demo cannot quietly run on stand-ins. Using an adapter that cannot be made raises `AdapterUnavailable`, which names the adapter, its service and any missing keys. Prompt 03 asked for "fake", "real" or "missing key" per adapter. We added "not built", for sandbox mode with the keys set but no real adapter yet: "real" would be false there, and "missing key" would send people looking for a key they already set. "missing key" wins over "not built", because adding the key is the step someone can take. "not built" disappears as the real adapters arrive. Optional services, such as the TF-IDF fallback embedder (prompt 39) and hash-only photo checks (prompt 37), will need a state of their own then; for now a missing Google Vision key shows as "missing key".

**Fakes are deterministic and record their calls.** They use no randomness and never read the clock. Each records what it was asked, in order, in `calls`. `FakeLLM` and `FakeSpeechToText` answer from a queue (`queue(...)`), then from an optional responder function, then with a fixed default: an echo of the prompt for text, `{}` for JSON, one transcript per file. `FakeEmbedder` counts words into 256 slots chosen by SHA-256, because Python's `hash()` changes from one process to the next; texts that share words come out close together. `FakeGateway` derives the PayPal order id from our order id, so a repeated checkout returns the same order, as PayPal does for a repeated `PayPal-Request-Id`. It needs `approve()` (what the simulated PayPal page will call) before `capture()`, and refuses a second capture. `FakeMessenger` numbers messages `fake-msg-0001`, `fake-msg-0002` and so on. In a fake-mode server these records grow for as long as it runs, which is fine for tests and demos.

**Tests always run in fake mode.** The root `conftest.py` sets `OPENSTALL_MODE=fake` and stops `Settings` from reading `.env` in `pytest_configure`, before any test module imports the app, which reads its settings once at import for CORS and the MCP host check. An autouse fixture clears the settings and registry caches around every test, so each test starts with fresh fakes. Tests get `fakes` (the fake objects the app is using in that test), `settings`, and `use_settings(**env)`, which rebuilds the app's settings from exactly the given variables. The suite passes with a developer `.env` in sandbox mode and with keys set in the shell.

**`GET /api/status` names keys and never shows them.** It returns the mode, the app version (the installed `openstall` package's) and, for each adapter, its name, label, purpose, real service, status, the keys the real service needs and, in sandbox mode, the ones not set. It never reads a key's value, only whether one is set. Tests set made-up values for every key, and a `DATABASE_URL` with a password, in both modes, and check that none appears in the response body or headers. Responses carry `Cache-Control: no-store`, so a browser never shows the mode from before a restart.

**The /status page loads in the browser.** As with the footer's API check, the page itself is static and a client component calls `/api/status` through `src/lib/api.ts`, with a 10-second limit and a "Try again" button. The mode is a large badge (Fake in amber, Sandbox in teal). The adapters are a two-column table: the adapter with its purpose and real service, then a status badge (Fake amber, Real green, Missing key red, Not built yet grey). With three columns, the descriptions were about 85px wide on a phone. Each row header is named by the adapter's name alone (`aria-labelledby`), so a screen reader does not read the whole description as the header. Key names are inline blocks that wrap only after an underscore, and only when wider than the column, so at 320px no name or full stop is left on its own. The badge colours are new tokens in `globals.css` (`--warning`, `--success` and `--danger`, each with a `-soft` background), with at least 4.5:1 contrast in both themes. The footer links to the page as "System status".

**One UI test answers `/api/status` itself.** The e2e API always runs in fake mode, so `e2e/status.spec.ts` checks sandbox mode (missing keys, one real adapter, one not built, no sideways scrolling at 375px) by fetching the real response and swapping in a sandbox body with `page.route`, keeping the real headers, CORS included. The other status tests use the real API.

**`build-config.test.ts` gives its ESLint check 30 seconds.** Building an `ESLint` instance with Next.js's config takes about 4 seconds on its own. On a busy machine it went past Vitest's 5-second default, and `npm test` failed at random.

**The local venv has pydantic-settings 2.16.0.** `pyproject.toml` asks for `>=2.16,<3`. When we added it, 2.16.2 was two days old and 2.16.1 ten days old, so the venv got 2.16.0 (October 14), in line with not installing packages days after their release.

## Offer rules and the allocator (prompts 22 and 25, spec 3.3 and 3.4)

The code is in `packages/allocator/openstall_allocator`: `types.py` (inputs and outputs), `rules.py` (offer checks and clocks) and `allocate.py` (the split).

- **Plain types, no infrastructure.** The package has its own frozen dataclasses (`SellerPolicy`, `Listing`, `QuoteRequest`, `Offer`, `OfferCheck`, `PlanLine`, `Plan`) and imports nothing from the database, the web or a model. The API maps its rows onto them. The spec's policy JSON maps directly: `SellerPolicy(**json.loads(policy_json))`.
- **Every type checks itself when it is built.** Money becomes a `Decimal` with exactly 2 places. `usd()` accepts `Decimal`, `int`, `str` or `float` (floats through their shortest repr, so `29.99` stays `29.99`). It refuses negative, non-finite and sub-cent amounts instead of rounding them, so a price is never changed silently. Counts must be ints, not bools or floats. Dates must be `date`, not `datetime`, because a `datetime` makes `(deadline - today).days` drop part of a day and can cost a seller a unit of capacity. `max_discount_pct` runs from 0 to 100 with at most 2 decimal places, which keeps every price calculation exact.
- **The lowest allowed price is rounded up to the cent.** It is `max(floor, list price × (1 − max discount))`, so for Amina it is $15.30, not her $15 floor. Offers are whole cents, so rounding up never changes which offers are valid. It does give the seller agent and the `/demo` panel an exact price to show. Seed values: Amina $15.30, Priya $13.60, Lucía $19.00, Grace $27.20.
- **Each offer gets one rejection reason:** the first failing rule, in this order: `below_floor`, `over_buyer_cap`, `over_capacity`, `too_soon`, `after_deadline`. `below_floor` covers both the floor and the maximum discount. The reasons are a `StrEnum`, so they compare equal to the strings stored in `offers.rejection_reason` and serialise as those strings. `OfferCheck` is falsy when the offer is invalid and unpacks as `valid, reason`, because prompt 22 describes the result as a pair.
- **Capacity is measured to the buyer's deadline, as in the spec code.** This is right because seller agents always offer delivery on the deadline (spec 3.3 step 1). If offers ever carry an earlier delivery date, measure capacity to that date instead, or an early promise could claim units the seller cannot make in time. `committed_units` (the seller's open order parts in the same window) is a keyword argument of `is_valid_offer` and is passed on to `capacity_available`.
- **A mismatched seller is a bug, not a rejection.** Checking Grace's offer against Amina's policy or listing raises `ValueError`.
- **Some proposals never become an `Offer`, so they get no rejection reason.** `Offer` refuses a quantity below 1 and a price that is negative, not whole cents or not a number (`ValueError`, or `TypeError` for `None` and other types), so `is_valid_offer` never sees such a proposal. Two normal cases hit this, and the seller agent and the quote rounds (prompts 23 and 24) must handle both:
  - A seller with no capacity left by the deadline (spec 3.3 step 1 then gives a quantity of 0, for example after a short deadline or committed units) makes no offer. Skip that seller before asking the model.
  - A model price such as `"29.995"`, `"-1"` or `"about $20"` is an invalid proposal. Catch the error, log the proposal in `offers` with `is_valid=False` and `rejection_reason="invalid_price"` (spec 3.3 step 6 logs every proposal), and retry with that reason like any other. Add `INVALID_PRICE = "invalid_price"` to `RejectionReason` at the same time, so every stored reason still maps onto the enum.
- **`SystemClock` uses UTC by default,** so every server and developer machine agrees on "today". `FixedClock` fixes the date for tests and for recording the demo.
- **One offer per seller.** Capacity belongs to the seller, so two offers from the same seller could promise the same units twice. `allocate` raises `ValueError` instead of guessing; callers pass each seller's best valid offer, which is what prompt 24 returns.
- **Stable order.** Offers are sorted by unit price, then earlier delivery, then seller id. With one offer per seller this order is total, so the same offers give the same plan whatever order they arrive in. Plan lines are in allocation order, cheapest first.
- **Cheapest first is optimal here.** With a single quantity target and a cap per offer, filling from the cheapest offer first gives the minimum cost the spec asks for. A property test checks this against brute force on small cases.
- **Fair share rounds up to a whole unit.** `fair_share=0.3` lets each seller take at most `ceil(0.3 × quantity)` units: 12 of 40, 13 of 41, 1 of 1. Rounding down would make small orders impossible (30% of 1 unit is 0) and could leave a shortfall caused only by rounding. The share is computed in `Decimal`: in floats, 0.07 × 100 is 7.000000000000001 and would round up to 8. Fair share is off by default, as in the demo.
- **Partial plans explain themselves.** When the offers cannot cover the quantity, the plan holds everything possible, with `complete=False`, the shortfall in units and a reason such as "Only 44 of 50 units can be supplied by 2026-12-10." The reason also says when late offers were left out, when fair share held back a seller whose on-time offer was bigger than the cap, or when nobody made an offer. A quantity of 0 gives an empty, complete plan.
- **A plan cannot carry a changed total.** `Plan` and `PlanLine` refuse totals that do not match their lines, so a plan rebuilt from stored JSON or sent back by an agent cannot change a price or total (spec 3.5: never trust a total from an agent).
- **Test data.** `packages/allocator/tests/conftest.py` holds the seed table from spec section 2. The tests check, for several run dates, that the capacities are 12, 11, 10 and 11, that no three sellers reach 40, and that the story splits 12, 11, 10 and 7 for $815.00.
- **Dependency.** The property tests import `hypothesis` (6.100 or later) at module level, so it must be listed in the `dev` extra of `pyproject.toml`. Without it, `pip install -e ".[dev]"` followed by `pytest` stops at collection on a fresh install. Hypothesis keeps its example database in `.hypothesis/`, which `.gitignore` leaves out.

## Trust passports: score, canonical JSON and signatures (prompt 35)

Code: `packages/trust/openstall_trust`. Spec: section 3.7.

- **Score.** `trust_score` is the spec 3.7 formula and returns a `Decimal` rounded half-up to 2 places. Each rate is read through `str()`, so 0.82 counts as 0.82 and not as its binary value 0.8199…. Otherwise rates such as 0.82, 0.02 and 0.91 (exactly 0.895) would score 0.89 instead of 0.90. Rates outside 0 to 1, NaN, infinities and booleans raise an error instead of being clamped, because they mean a bug upstream.
- **The score ignores the caller's decimal settings.** It is worked out in its own decimal context (400 digits, half-up), so a module that lowers the precision or traps rounding for its own money maths cannot change or break a score. Every step is exact for any float rate and for `Decimal` rates with up to 399 places, so the score is rounded once, at the end. With more places than that, the steps are rounded to 400 digits before the final rounding.
- **What gets signed.** The signature covers `canonical_json(passport)`: keys sorted at every level, no whitespace, text as UTF-8 (not `\u` escapes), and the top-level `signature` field left out. Nested fields named `signature` are signed like any other field.
- **Whole-number floats up to 2**53 are written as integers** (1.0 as 1). Browsers do the same, so a passport that goes through `JSON.parse` and `JSON.stringify` (the tamper-check panel, prompt 38) still verifies. Rates of exactly 1.0 or 0.0 will be common once prompt 36 adds live deliveries.
- **The limit: bigger whole numbers do not survive a browser.** `JSON.stringify` writes the float 2.0**60 as the integer 1152921504606847000. Python reads that back as an `int`, and `canonical_json` writes it differently from the float it signed, so the passport no longer verifies. This happens to every whole float above 2**53 and below 1e21 in size. From 1e21 on, browsers write exponent notation such as `1e+21`, which Python reads back as the same float. Integers above 2**53 can break too, because the browser keeps only a float's precision: 2**60 comes back as 1152921504606847000. Counts and rates never come near this size. A field that needs such numbers should hold them as strings.
- **Not RFC 8785.** Other numbers keep Python's spelling, which matches JavaScript for everything a passport holds (counts, and rates of 0.0001 or more). Someone checking passports outside Python should use `POST /passport/verify` or port `canonical_json` exactly.
- **Only plain JSON can be signed.** NaN and Infinity raise `ValueError`. Non-string keys, sets, bytes, `Decimal` and `datetime` raise `TypeError`: convert them first (`float(score)`, ISO time strings). `Decimal` is refused because encoders disagree on it (Pydantic writes a string, FastAPI's encoder a float), so its signed form would be ambiguous.
- **Nesting is capped at 32 objects or arrays.** `POST /passport/verify` will accept JSON from anyone, and real passports nest one or two levels.
- **Signature format.** `ed25519:` followed by the 64 signature bytes in base64url without padding (86 characters). Verification accepts only that exact spelling. Python's decoder skips stray characters and ignores the spare bits of the last character, so without this check one signature would have many accepted spellings.
- **Keys.** Raw 32-byte Ed25519 keys as standard base64 (44 characters), not PEM: one short line fits in `.env` and in the host's settings, and it is the form most Ed25519 libraries take. `PASSPORT_SIGNING_KEY` holds the private key, and `scripts/make_signing_key.py` makes a new pair. Loading rejects anything else, base64url included, with an error that never repeats the input, since the input may be the secret.
- **`verify_passport` never raises for a bad passport.** Tampering, a missing or malformed signature, content that is not plain JSON, or another key's signature all return `False`. Passing something that is not an Ed25519 public key is a programming error and raises `TypeError`.
- **The trust package reads no settings.** The API reads `PASSPORT_SIGNING_KEY` and passes keys in, so tests and scripts can use their own keys.

## November 1: the database (prompt 04)

Code: `apps/api/openstall_api/db.py` (engine, sessions, migrations, the `Money` type) and `models.py` (the tables). Migrations: `apps/api/openstall_api/migrations`, inside the package, so they ship with it to the host.

- **Two tables the spec did not list.** `chat_messages` holds every message in a seller's chat, inbound and outbound, with its media, transcript and language: the spec's `chat_sessions` keeps only the state and the draft. `processed_webhooks` records each webhook event id once handled, so a repeated PayPal or Twilio webhook changes nothing (spec section 7).
- **Pay-on-proof shapes the order tables.** Orders go `draft → awaiting_approval → authorized → partly_shipped → shipped → completed` (or `cancelled`). Each seller's share is an `order_parts` row with its own status (`pending → authorized → captured → delivered`, or `released`), its PayPal `authorization_id` and `capture_id`, and its tracking. A top-up order from a self-healing re-plan points at its order through `parent_order_id`.
- **Money is exact on both databases.** The `Money` column type is NUMERIC(10, 2) on Postgres and whole cents in an INTEGER on SQLite, which has no exact decimal type. Integer cents also keep comparisons inside the database right (on SQLite as text, "10.00" would sort before "9.00"). Every amount goes through `openstall_allocator.usd`, so negative or sub-cent amounts are refused rather than rounded.
- **Enums are text with a CHECK constraint,** not database enum types: the same on SQLite and Postgres, easy to extend in a migration, and an unknown value is refused both by the model and by the database itself.
- **IDs are readable prefixed strings** (`s_amina`, `ord_3f9a1c7e2b40`), made in Python. The exception is `events`, whose id is an increasing integer so the live feed (prompt 05) can ask for "everything after event 41".
- **Every foreign key has a `relationship()`.** SQLAlchemy orders inserts by relationships, not by bare foreign keys, so without them a seller's passport or chat session could be inserted before the seller.
- **SQLite enforces foreign keys** (`PRAGMA foreign_keys=ON` on every connection), so tests catch what Postgres would refuse.
- **`DATABASE_URL` is a secret setting.** `postgres://` URLs from hosts are rewritten for the psycopg driver, and a relative SQLite path is taken from the repo root. `/api/status` reports the database as ok (with rows per table), "not migrated" (with the missing tables) or "error" (with only the error's type, never the URL).
- **Migrations run at start-up when `AUTO_MIGRATE` is on** (the default for local runs). The hosted demo will run `alembic upgrade head` in its start command instead (prompt 12). After changing `models.py`, make a migration with `alembic revision --autogenerate -m "..."`; `test_db_migrations.py` fails if a model changes without one.
- **Each test has its own SQLite file.** The root `conftest.py` points `DATABASE_URL` at a file in the test's temporary folder, and the `db` fixture creates the tables and gives a session. `use_settings()` keeps that database unless a test passes its own `DATABASE_URL`.

## November 1: the event log and the live feed (prompt 05)

Code: `apps/api/openstall_api/events.py` (event types, `record_event`, the stream), `events_api.py` (HTTP), and in the web app `src/hooks/use-event-stream.ts` and `src/components/live-activity.tsx`.

- **Every event carries a one-line summary in plain English,** written by the code that records it (for example "Amina was paid $216.00 on proof"). The feed shows it as is, so the wording lives next to the action and the web app needs no per-type templates. It is stored in the payload under `summary` and returned as its own field.
- **`record_event` does not commit.** It adds the event to the caller's session, so an action and its event are saved or rolled back together, and the audit log never claims something that did not happen.
- **Payloads stay exact.** Money becomes a string such as "216.00" (a float would round), dates become ISO strings, and enums their values. Anything else is refused with a clear error.
- **All event types live in `EventType`.** An unknown type is refused, so a typo cannot create a type the feed has never heard of.
- **The stream polls the table** every half second instead of listening in-process, so it also sees events written by other server instances or scripts. Each message's id is the event id: a browser that reconnects sends it back as `Last-Event-ID` and misses nothing. A comment ping every 15 seconds keeps proxies from closing a quiet stream.
- **The page loads past events first, then follows the stream from the last one it has** (`?after_id=`), so nothing falls in the gap between the two. Events are shown newest first and only once, however often they arrive.

## November 3: the APIMatic PayPal SDK (Best Use of APIMatic)

Code: `packages/paypal/openstall_paypal/sdk.py` (the SDK client, its transport, retry policy and error boundary), `sandbox.py` (the gateways on top of it), `apps/api/openstall_api/claims.py` with migration 0005, the PayPal section of `/status`, and `paypal-plan.md` at the repo root (the contract sheet).

- **Orders and Payments go through APIMatic's PayPal Python SDK,** built with APIMatic's PayPal Context Plugin. Every SDK fact the code uses (signatures, wire names, error unions, enum members) was looked up in the SDK's map and source and written into `paypal-plan.md` before any code changed. The SDK is pinned in `pyproject.toml` to its full commit hash, `143e57f2a372…` (version 2.29); it is not on PyPI, so pip installs it from git, which needs `allow-direct-references` in hatch.
- **What the rest of the app sees.** The `PaymentGateway` interface, both payment paths and their payloads, the idempotency keys (sent as `PayPal-Request-Id`), the capture's `invoice_id` and the approval-link rule are as before, and the old gateway tests still pass against the SDK. Two things changed: `PaymentUnavailable` now says whether the request may have landed, and the checkout and reserve endpoints have a new 409 (below).
- **Payouts and webhook verification stay on our own client.** The SDK has no Payouts or Notifications operations, so a gateway now holds two clients for the same REST app. The status page's token check also uses our client.
- **The sync client.** Our endpoints are plain `def`, run in FastAPI's thread pool, so the SDK's sync `PaypalClient` is the right one; the async client would need `await` everywhere. It is made once per process and shared across threads, and the registry closes it at shutdown. The base URL is always passed: left out, the SDK silently uses the sandbox.
- **Retries: reads only.** The SDK retries by default. We keep that for `get_order` (two retries, short waits) and never let it resend a write: a capture that got no answer may have landed, so the caller reads the state back, as spec 3.5 requires. A 401 is the one exception we handle ourselves: the SDK drops its token but does not resend, so we resend once with a fresh token and the same `PayPal-Request-Id`, as our old client did. That holds whatever the 401's body says: PayPal's usual ones (`invalid_token` for an expired token, `AUTHENTICATION_FAILURE` without a `debug_id`) do not fit the SDK's `Error` model and come out of the SDK as a decode failure rather than `ApiError`, so the boundary goes by the status the transport recorded. The tests use those real bodies.
- **One error boundary.** A refusal becomes `PaymentError` with PayPal's issue code (`details[0].issue`, else `name`), even when PayPal's error body is not the shape the SDK expects. A 5xx, a timeout or a dropped connection becomes `PaymentUnavailable`, which now says whether the request may have landed: a refused connection, or a failed token fetch, never reached PayPal; a read timeout may have. An answer the SDK cannot read is treated as possibly successful, never as a failure. A void answered with an empty 204 is a success.
- **Duplicate claims.** Each PayPal write a caller can ask for twice (checkout, reserve, a share's capture, its void) is claimed first in a new `paypal_claims` table, keyed by what it is for, so two requests are never calling PayPal for one write at once; before this, on SQLite, two requests could both get through.
  - **On Postgres the claim is written in the request's own transaction.** Every flow already locks the order's row first, and the uncommitted primary key blocks a second insert, so that is just as exclusive, and a request needs one pooled connection, not two. A claim on a second connection, taken while the order's row was locked, let about 15 concurrent payment requests drain the pool (5 + 10) and fail after 30 seconds. The claim is marked done in the same commit as our rows.
  - **On SQLite the claim is committed on a connection of its own**, since SQLite takes no row locks; if the request has already written, it joins the request's transaction instead, since SQLite has one writer at a time. It is marked done after the request commits. If that fails, it is logged rather than turning the saved request into a 500.
  - **A refusal releases the claim.** When the holder finishes without PayPal's answer saved (PayPal did not answer, or the request rolled back), the claim is marked unknown. The next request for the same write, with the same `PayPal-Request-Id`, goes ahead at once, and PayPal answers it with the first result if the first landed, as before claims. A pending claim older than 2 minutes (a process that stopped mid-call) is taken over, with a compare-and-set so only one request can.
  - **The new 409**, from `POST /api/orders/{id}/checkout` and `/reserve` (and the capture and release services): "Order … is being sent to PayPal by another request. Try again in a moment." (or "… is being reserved at PayPal …", "…'s share is being paid / released …") while another request holds the claim; and "PayPal did not answer an earlier attempt at this. Try again after HH:MM UTC." for an unknown claim with a different `PayPal-Request-Id`, until it is stale.
- **Tests fake PayPal at the SDK's seam,** a transport passed as `custom_http_client`, and check the request the SDK really built. They cover every failure kind the plugin lists, the retry policy, and the claims, including eight requests racing for one claim and a count of pooled connections on the Postgres path. The claims tests run on SQLite only: there is no Postgres server on the development machine.
- **/status names the SDK** in its PayPal section ("APIMatic PayPal Python SDK 2.29", with its commit), read from the installed package. In fake mode it says no SDK is in use.
- **Not yet tried against the real sandbox.** The plugin asks for a read-only call of each operation with the real keys before the sheet is final; there are no PayPal REST keys yet, so that is pending in `paypal-plan.md`.

## November 3: real search with filters (prompt 20)

Code: `apps/api/openstall_api/search.py` (matching, filters and the search log), `offer_rules.py` (database rows on the allocator core), `storefront.py` (the tool), `search_api.py` (`GET /api/searches`), and in the web app `src/components/agent-searches.tsx`, `src/hooks/use-live-list.ts`, `EventStreamProvider` in `src/hooks/use-event-stream.ts`, and `e2e/support/mcp.ts`.

- **Matching in plain Python.** A listing's title, description, category and colours become words: lower case, accents dropped and plurals made singular, so "CUSHIONS" finds "cushion" and "cojin" finds "Cojín". A query word the listing has scores 2; a word of at least 3 letters that only starts one of its words ("embroid") scores 1. Best score first, then the lower price, at most 50. Stop words ("for", "with", "the" ...) and bare numbers are dropped from the query: every seeded description says "16 by 16 inches, with ...", so "mugs with 16 oz handles" would otherwise find every cushion. At this catalog's size a scan in Python costs nothing and SQLite and Postgres behave the same; Postgres full-text search can replace it when the catalog grows.
- **What counts as a match.** A listing is found when it has at least half of the query's words (rounded up) and at least one of them is in its title or category. At first any one word was enough, so colours and description words found the covers for unrelated searches ("red ceramic mugs" found Amina's red cover, "cotton tote bags" every cotton cover) and those searches were never logged as finding nothing. Now a colour or a description word alone finds nothing; it only adds to the score of a listing its title or category finds, so "teal cushions" puts Amina's first. Half rather than every word, so the whole story request ("40 hand-embroidered cushion covers for corporate gifts", 6 words) still finds all five covers: Lucía's and Noor's have 3 of its words. A two-word search needs one word, so a search that shares one title word with a listing still finds it ("hand towels" finds the hand-embroidered covers); telling the thing wanted from the words around it is left for a real search engine.
- **Capacity comes from the allocator core.** `offer_rules.py` maps a seller's policy JSON onto `SellerPolicy` and a product onto `Listing`, and `capacity_by_deadline` calls the core's `capacity_available`, so search shows the seed table's 12, 11, 10 and 11 (10 for Noor) for a 30-day deadline. Prompt 22 extends this module instead of mapping again. Capacity per week comes from the policy JSON when it has one, else from the listing, because onboarding takes it from the listing (prompt 18). A missing field, or a value the core refuses, is a `PolicyError` naming the seller and the field. Search leaves such a listing out, with a warning in the log, since its maker could not be quoted either.
- **Committed units are her reserved shares, and only those.** A share counts while it is `authorized`: the human approved, PayPal holds the money, and she has not shipped. A `pending` share is a draft nobody approved: any agent can make one for free, and the seeded `ord_demo` is one, so counting drafts would let drafts block makers and would break the seed table's numbers. A `captured` or `delivered` share is made and shipped, and a `released` one is off. Every reserved share counts, whatever its date, not only those due by the deadline asked about: she cannot make two orders' covers in the same days. This can under-promise when a reserved share is due long after the deadline, but it never sells time she has already sold.
- **So a reserved story order uses up the story.** Each one takes the four makers' 30-day capacity: a second run in the same database finds them fully booked. Demo runs start from a fresh seed (prompt 29's reset, and section 7's "twice in a row from a fresh seed"). In the shared e2e database, `approve.spec.ts` and `pay-on-proof-fake.spec.ts` reserve story orders before later spec files run, so a later UI test must not count on what a maker has left; prompts 24 and 29 will need a reset or a fresh database for theirs.
- **The filters.** `max_price` leaves out dearer listings. It is held to whole cents, rounded down (29.999 becomes 29.99, 30 becomes 30.00): every price is whole cents, so this finds exactly what the exact cap would, and the log, the feed and the panel show the cap the filter applies instead of a rounded one. `deadline` must be after today (UTC); without one, capacity counts to today + 30 days, and the tool description says so. With a `deadline` or a `quantity`, makers who can make no unit in time (production days after the listing's ship days) are left out; the others stay in with their `capacity_by_deadline`, because OpenStall pools makers and nobody has to make the whole quantity. With neither, every match is listed, a fully booked maker with capacity 0. `ship_to` is a city we cannot place yet: for now each listing's ship days are taken as days to a US city, as the tool description says, and the city is only logged.
- **A deadline sooner than a maker's lead days gives her no capacity.** `capacity_by_deadline` returns 0 when the deadline is before today + her `min_lead_days`, whatever her production time says. Seller agents always offer delivery on the deadline, and `is_valid_offer` refuses a delivery that soon (`too_soon`), so search must not list her as able to make units in time. The core's `capacity_available` stays exactly as spec 3.3 writes it. No seeded maker is affected: their ship days already give 0 before day 5.
- **Every search is logged, except refused ones.** One `searches` row (the query with its spaces tidied, the filters the agent gave, the result count) and a `search.logged` event such as `An agent searched for "ceramic mugs": no results.`, in one transaction. The default deadline is not stored as a filter, since the agent did not ask for it; `max_price` is stored in whole cents as a string ("30.00"). A search refused for bad input (a past deadline, a price under one cent, a blank query) is not logged.
- **The buyer's words are quoted safely, and control characters are refused.** `/mcp` is public and the feed on /demo is public, so the summary quotes the query and the city as JSON strings: a quote mark inside is shown as `\"` and cannot end the quotation, so nothing a caller types reads as OpenStall's own sentence (such as a fake "Confirmed by PayPal"). The panel reads the words from the payload, not the summary. Spaces, tabs and line breaks are tidied to one space; any other control character in the query or the city is refused with the reason, because Postgres cannot store NUL and the agent would otherwise get only "Error executing tool".
- **search_products is not marked read-only.** It never spends money and changes no order, but each call adds a row that /demo shows to anyone, query and city included, and MCP's `read_only_hint` means "does not modify its environment". So it is `read_only_hint=False` with `destructive_hint=False` (it only adds), `idempotent_hint=False` and `open_world_hint=False`, and its description says the log is public and asks agents to leave names and other personal details out. An MCP client may ask its user before the first search because of this; that is the honest trade. (At first the tool kept `read_only_hint=True`, on the view that the log is OpenStall's own record of demand; the reviewers' point that the words are shown publicly changed it.)
- **What a result says.** The listing, now with its description; the maker's name; `trust`: her score as a number, delivered orders, on-time and dispute rates, its data_source, and one line such as "Trust score 0.97 from 25 delivered orders: 96% on time, 0% disputed (seeded demo numbers)"; the listing's `data_source`; `capacity_by_deadline`; and the `deadline` it counts to. Prices stay numbers for agents (prompt 06).
- **Every parameter is documented in the schema.** The MCP SDK does not read a docstring's Args section into the input schema, so each parameter is `Annotated[..., Field(description=...)]`. The SDK also checks the limits (a price from $0.01 to $1,000,000, a quantity of at least 1, a query of up to 300 characters, a city of up to 120) and refuses with the reason. A test lists the tools over HTTP and checks that every parameter of every tool has a description.
- **/demo's "Agent searches" panel** loads the recent searches from `GET /api/searches` (newest first, `limit` 1 to 100, 20 by default) and adds each new one from its `search.logged` event. A search that found nothing is an amber row that says "No results"; its badge is an outlined pill on the surface colour (`Badge outline`), since an amber-filled badge would vanish into the amber row. If the earlier searches cannot be loaded, the panel says so and does not also claim that no agent has searched. Each search that arrives after the panel opens is announced to screen readers by a polite status line ("New search for “ceramic mugs”: no results."); the first rows it loads are not, so opening /demo does not read out 20 searches.
- **One event stream per page, and a pattern for live panels.** `EventStreamProvider` wraps /demo's panels, and `useEventStream()` inside it returns the provider's stream instead of opening its own. Otherwise each live panel would hold a connection of its own and poll the events table twice a second, and browsers allow only 6 connections to a host over HTTP/1.1. Later panels (offers, rounds, allocation, the draft order) use `useLiveList(source)` the same way: a source defined once, outside the component, says how to load the recent rows, how to read a row from an event, and each row's key and time; the hook shows each row once, newest first.
- **useLiveList keeps its own rows.** The stream keeps only the latest 200 events (`MAX_EVENTS`), so rows rebuilt from that window on every render would drop a row once 200 newer events of any kind arrived, while older loaded rows stayed. The hook reads each event once, oldest first, into rows it keeps, trimmed to the source's `limit`. Of two versions of a row (one key), the newer by `time` stays, and on a tie the one read later: so the latest event about a row wins, and an event from the backlog that is older than a freshly loaded row does not replace it. A panel whose rows change (an order going from drafted to authorized) must give `time` as when the row last changed.
- **UI tests search through the real MCP endpoint.** `e2e/support/mcp.ts` is a small MCP client: JSON-RPC `initialize`, `tools/list` and `tools/call` posted to the e2e API's `/mcp`, which is stateless with JSON responses, so it needs no session.

## November 4: the plan explained in words (prompt 26)

Code: `packages/agents/openstall_agents/explain.py`, `apps/api/openstall_api/allocation.py` (`plan_quote` stores the words with the plan), `orders_api.py` and `seed.py`, and in the web app `src/components/allocation-panel.tsx` and `approval-view.tsx`.

- **The model writes, code checks every number.** `explain_plan` asks for 2 or 3 plain sentences (why these makers, why this split, the total, the delivery date) with the facts as JSON, each number formatted once. `ungrounded` then reads every number in the answer, money, dates, digits with commas and number words ("four", "forty"; "half" and "dozen" never pass), and the words are used only if each one is in the plan or the request. Planning the same quote again keeps the stored plan and its words: the model is asked once per plan. The quote commits its own writes before the model is asked, so nothing is locked while it answers.
- **Shown where a person decides:** under the allocation on /demo, and first on `/approve/{id}`, as "Why this split". The seeded story order gets the story's plan and the template's words at seed time, so the approval page explains the split before any agent has run.
